\section{The \texttt{.tt} Container and Security Design}
\label{sec:container}

\subsection{Creating and reading the current file}
A \texttt{.tt} file carries one complete itinerary snapshot. On export, the Creator reserves a revision in SQLite, reads the trip, and maps its days, events, and documents into a shared \texttt{TripPackage}. The export use case serializes the metadata and appends the unique attachment blobs. The Dart adapter writes the binary envelope described in Table~\ref{tab:container}. The inner stream begins with a four-byte big-endian metadata length, followed by UTF-8 JSON and the attachment bytes. The itinerary ID and revision travel inside the JSON. The stable format uses the envelope version and flags to select a decoder.

The Viewer checks the \texttt{TTRV} marker, reads the payload length, and reverses the XOR wrapper. It decodes the JSON, checks attachment bounds and the applicable digests, and saves the trip if the revision rules accept it. TripyTravy supplies the official writer and reader for this application format. The extension and marker identify the expected layout. A compatible third-party program could read or produce the same bytes.

The beta applications use the Dart wrapper. It uses a fixed derived byte for ordinary exports and reduces a supplied PIN to one byte in the optional adapter path. The trailer check depends on the derived byte and flags. The application export and import screens do not provide the planned secure PIN workflow. The standalone Rust library implements AES-256-GCM, and neither Flutter application calls that library in the evaluated build. The two adapters share header fields and use incompatible payloads and trailers. A production reader needs explicit format dispatch. A failed authenticated import must terminate without a legacy-decoder fallback.

\subsection{Salt and key derivation in the Rust prototype}
The architecture specification describes AES-256-GCM with a per-file salt and two key derivation modes. The Rust code generates a fresh 16-byte salt $s$ and 12-byte nonce $n$ for each export and writes both to the header. It reconstructs a 32-byte seed $S$ from constants. In standard mode, the keying input $I$ is $S$. In PIN mode, the library takes the PIN $P$ and computes
\begin{align}
D &= \operatorname{Argon2id}(P,s;m,t,p,L), \\
I &= S \,\|\, D,
\end{align}
where $\|$ denotes concatenation. The prototype uses 19,456 KiB of memory, two passes, one lane, and a 32-byte output for $D$ \cite{argonrfc}. In either mode the 32-byte AES key $K$ is
\begin{align}
R &= \operatorname{HKDF\!-\!Extract}(s,I), \\
K &= \operatorname{HKDF\!-\!Expand}(R,\ell,32),
\end{align}
with SHA-256 and a separate context label $\ell$ for standard and PIN mode \cite{hkdfrfc}. The export does not store the key, seed, or PIN in the header.

The design specifies Protobuf metadata for the native format. The standalone library accepts serialized bytes from its caller and does not perform that serialization itself. It compresses the length-prefixed stream with Zstandard and encrypts it with AES-256-GCM under $K$ and nonce $n$. It authenticates the 40-byte header as associated data and appends the 16-byte tag \cite{gcm}. On import, the reader uses the salt from the received header, the same derivation procedure, and the entered PIN when required. Matching inputs reproduce $K$. The reader uses the stored nonce and checks the authentication tag before decompressing. A wrong PIN typically gives a different key, so authentication fails. The importer generates no new salt for decryption. The per-file key controls decryption, while the itinerary ID matches the trip across revisions.

\subsection{Five-attempt policy in the stable design}
The stable design includes a local attempt policy for protected imports. After five failed authentication attempts on a writable import copy, the Viewer overwrites part of that copy's ciphertext. The altered copy then fails GCM authentication even with the correct password. The policy acts on the incoming file and leaves any saved itinerary untouched. A file received from a sharing application may only be available as a read-only stream. In that case the policy can act on a private staging copy. Originals retained by the sender, messaging application, or recipient remain usable, and a separate reader can make offline guesses. The policy can also deny a legitimate traveler access to the affected copy. Its implementation and behavior on device are outside the beta measurements.

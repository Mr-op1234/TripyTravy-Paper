\section{Results}
\label{sec:evaluation}
We evaluated several beta builds and the standalone Rust prototype. The app results cover host tests, interoperability checks, and release builds. Device behavior is discussed separately.

\subsection{Functional and revision tests}
In the first run, 52 desktop tests, 23 mobile tests, and 13 Dart core tests passed. Three separate Rust tests checked round-trip packing, PIN handling, and rejection of a modified authenticated header in the standalone prototype.

In the follow-up, 54 desktop tests, 23 mobile tests, and 13 Dart core tests passed. The synthetic package sizes and metadata mutation result matched the first run. The follow-up focused on host suites and synthetic cases, with the native Rust tests and legacy migration covered in the earlier evaluation.

The desktop tests cover date-based records, event and document persistence, description formatting, image-upload controls, and export naming and metadata. The mobile tests cover picker import, day navigation, photo-gallery behavior, document presentation, and the ordered map URL. These tests exercise application logic and widgets. The Android platform handoffs were verified by source inspection.

The revision tests submit a newer snapshot and then earlier files to one service instance. The repository keeps one entry at the newer revision. Other cases cover identical legacy numbers on unrelated trips and rejection of a positive revision attached to a non-versioned ID. The desktop export test checks the exported identifier and verifies that reserving the next revision advances its counter.

The file-based client probe imported a legacy itinerary and checked one packing item. It then exported and imported revision~1 with a permanent ID and a revised title. The repository held one trip with the new title and the item still checked. Reopening the original file left revision~1 in place. Separate application tests cover the desktop export control and mobile picker.

\subsection{Protected exports and imports}
The protected beta passed 54 Creator tests, 24 Viewer tests, and 15 Dart core tests, for a total of 93. In host tests, the Viewer imported with the correct passphrase, allowed cancellation at the prompt, and rejected a wrong passphrase or a change to the header, ciphertext, or authentication tag. A revision encrypted with a new passphrase replaced the schedule and kept the checklist and completion state. Replaying older files left the saved revision in place. The importer also rejected a newer unprotected revision for that entry.

The Dart codec decrypted a synthetic file made by an independent Node.js implementation, which in turn decrypted a Dart export. The Windows Creator and Android Viewer release builds succeeded. We verified the Android APK signature under the project's development signing configuration. We did not test handset delivery or offline reopening after restart in this run.

The protected-format rerun reproduced all six sizes. From two to eight references, the package with a shared payload grew by 1,284 bytes because the additional records needed metadata and reused the same blob. The fixtures use exact byte matches. Savings for an actual trip depend on how often passengers need the same attachment.

\subsection{Legacy limitations and regression checks}
The earlier decoder accepted altered synthetic metadata. In a separate test, the earlier importer rejected a malformed legacy trip after writing an asset in the isolated test directory. The protected beta rejected changes to authenticated files. Its legacy regression test also rejected an invalid attachment before writing any test blobs. Legacy exports still lack cryptographic confidentiality.

\section{Introduction}
An itinerary may specify where a traveler should be at a given time and carry the voucher needed at that location. A last-minute change has two consequences. The agent must send the revised schedule, and the traveler must be able to identify which version to follow. A hosted itinerary can keep a shared link current. The recipient still needs to receive the new data before leaving network coverage.

TripyTravy uses a file to carry the schedule, its attachments, and revision information. The agent edits a trip in the desktop Creator. The traveler imports a copy in the mobile Viewer and reads it from local storage. An agent can send the file over an existing channel, and the Viewer can process it once it is available on the device. The file and local repository provide the data for import and display. No TripyTravy service participates in those operations.

The system uses a single-author publishing model. The Creator maintains the editable itinerary, and the Viewer stores the most recent accepted snapshot it has received. Travelers can manage their own checklist and mark a trip complete. Their local state does not participate in itinerary authoring. In this paper, decentralized delivery refers to exchange without a central itinerary server. The workflow uses explicit file transfers and has one publishing authority per trip.

This paper specifies the stable Creator and Viewer workflows, including offline maps, typed event cards, protected file exchange, and password changes through revised exports. It uses the available beta and a standalone Rust prototype to evaluate specific parts of that design. The functional comparison with Travefy follows the agent's work from creating a day and scheduling an event to the traveler's use of a voucher at the destination. The experiments measure revision replacement, the size effect of exact-content deduplication, and how the beta wrapper handles altered metadata.

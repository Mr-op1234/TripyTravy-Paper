\section{Revision Handling}
\subsection{Identity and export ordering}
On the first versioned export, the Creator assigns the trip a random identifier and saves it with a revision counter. It reserves the next revision in a database transaction before compiling the file, so a failed export can leave a gap. Renaming the trip keeps its identifier.

\subsection{Acceptance and replacement}
For a versioned import, let $i$ be the trip identifier, $r$ the incoming revision, and $r_s$ the saved revision if there is a matching versioned entry. The beta decodes the file and validates its assets before comparing revisions. It also authenticates a protected package before comparing revisions and rejects an unprotected replacement for a previously protected entry. The following rule applies once those checks pass.
\begin{equation}
\operatorname{decision}(i,r)=
\begin{cases}
\text{create}, & \text{no matching entry},\\
\text{replace}, & r>r_s,\\
\text{keep saved}, & r\leq r_s.
\end{cases}
\label{eq:revisions}
\end{equation}
The Flutter picker and Android file-open action use the same import service. Each service instance queues its imports so that one revision decision finishes before the next begins. To replace a saved trip, the repository stages the complete snapshot and renames it into the existing trip path. The checklist stays in a separate record under the same trip ID, and the importer copies the local completion flag to the accepted trip. The original transfer file may remain in the sending app or in Downloads.

The stable interface distinguishes a newly saved itinerary, a successful replacement, a retained newer itinerary, and a rejected package. If the saved entry is deleted, the beta can accept a subsequent valid file as a fresh trip because the revision check consults the saved entry. An import with no matching stable identifier also creates a separate entry even if two titles match.

\subsection{Migration from numeric identifiers}
Older exports carried a numeric SQLite row ID. Two Creators with separate databases could issue the same number. A versioned package carries the former ID for migration. The Viewer migrates a saved legacy entry when that ID matches and the two trips share at least one event identifier. It transfers the checklist and completion state, saves the versioned record, and removes the legacy entry. With no shared event, the Viewer saves the incoming trip separately. Once the permanent ID is in use, it applies (\ref{eq:revisions}).
